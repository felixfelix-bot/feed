# Binary feed publishing — tag → release → indices → gh-pages

This document describes how a tagged build becomes a consumable OpenWrt
binary feed. Workflow: [`.github/workflows/build-feed.yml`](../.github/workflows/build-feed.yml).
Test: `sh tests/test-index-feed.sh`.

## The problem it solves

`validate-feed.yml`'s `build-sdk` job compiles `tollgate-wrt` per SDK target
(x86-64, mediatek-filogic, ramips-mt7621) and uploads the packages as
**workflow artifacts** — which expire with the run and are invisible to
routers. A router needs a stable URL serving per-architecture
`APKINDEX.tar.gz` (apk, OpenWrt ≥ 24.10) and `Packages.gz` (opkg) with the
`.apk`/`.ipk` blobs sitting next to the index. `build-feed.yml` is the
bridge between those two worlds.

## Targets vs arch tuples — why two names for the same hardware

| SDK target (build axis) | arch tuple (feed/consumer axis) | device example |
|---|---|---|
| `x86-64` | `x86_64` | x86 gateways |
| `mediatek-filogic` | `aarch64_cortex-a53` | GL-MT6000 |
| `ramips-mt7621` | `mipsel_24kc` | GL-MT3000 |

SDK images are published **per target**; feed consumers (feeds.conf,
`/etc/apk/repositories`) key URLs on **arch tuples**; the tuple is what the
built package itself declares in `.PKGINFO` (`arch = aarch64_cortex-a53`) /
control (`Architecture:`). The feed layout uses tuples — never target names.
`scripts/target-to-arch.sh` is the single source of truth for the mapping
(extend it when adding SDK targets); `scripts/artifact-arch.sh` reads the
tuple embedded in a package file.

## Pipeline

```
tag push (vX.Y.Z)
  └─ validate-feed.yml builds per-target .apk/.ipk      (workflow artifacts)
       └─ build-feed.yml [workflow_run, tag refs only]
            ├─ bridge          (ubuntu) stage THIS run's per-target artifacts
            ├─ index           (openwrt/sdk container — apk-tools3 REQUIRED*)
            │                  verify embedded tuple == target-to-arch.sh map
            │                  index-feed.sh per target dir
            │                  -> feed/<tuple>/{*.apk, APKINDEX.tar.gz, Packages.gz}
            ├─ publish-release (ubuntu) create release vX.Y.Z (if missing);
            │                  upload feed-vX.Y.Z.tar.gz, <tuple>-APKINDEX.tar.gz,
            │                  <tuple>-Packages.gz, and tuple-suffixed packages
            │                     tollgate-wrt-0.5.0-r1_aarch64_cortex-a53.apk
            │                  (flat release assets can't hold 3× the same
            │                   canonical filename; the suffix disambiguates)
            └─ publish-pages   (ubuntu) deploy feed/ to gh-pages (Q3 default)
```

**\*Why the indexer runs in an OpenWrt SDK container:** 25.12 packages are
**APKv3** (apk-tools3 `ADBd` container — verified against a real SDK-built
`tollgate-wrt` artifact; it is *not* a tarball and its arch is not
recoverable with shell tools). Plain-ubuntu runners have no apk-tools3, so
indexing runs inside the pinned `openwrt/sdk:x86-64-v25.12.5` image (index
generation is host-arch-independent). Outside such a container the scripts
**fail loudly** (`artifact-arch.sh`, `index-feed.sh`,
`generate-apk-index.sh`) rather than silently publishing an empty feed —
APKv2 tarballs and .ipk still parse with plain shell tools.

Alternative entry points:

- **release published** — re-indexes whatever assets are attached (a
  release manager can add packages by hand; arches are detected from
  embedded metadata, not filenames).
- **workflow_dispatch** with `artifact_release=<tag>` — manual re-index of
  an older release.

Indices are generated by `scripts/index-feed.sh` (restored from PR #1,
augmented for APKv3 — see above): grouping delegates to
`artifact-arch.sh` (single source of parsing truth), and unreadable
artifacts abort the run instead of being skipped. `apk` index generation
prefers the native binary and keeps PR #1's POSIX fallback for APKv2.
Empty releases are not a failure. Suite: `sh tests/test-index-feed.sh`.

## Release procedure

1. `scripts/sync-from-upstream.sh vX.Y.Z`, land it on `main` (normal PR).
2. Wait for `validate-feed.yml` green on `main`.
3. `git tag -s vX.Y.Z && git push origin vX.Y.Z`
   **Merge first, tag second** — `workflow_run` only fires for workflows
   that already exist on the default branch.
4. The bridge creates the release, uploads assets, indices land on the
   release and on gh-pages. Verify:
   `curl -fsSL https://freedomtechfeed.github.io/feed/aarch64_cortex-a53/APKINDEX.tar.gz | file -`

## Consuming the feed

OpenWrt ≥ 24.10 (apk):

```sh
echo "src/gz tollgate https://freedomtechfeed.github.io/feed/<tuple>/" >> /etc/opkg/customfeeds.conf
echo "https://freedomtechfeed.github.io/feed/<tuple>/" >> /etc/apk/repositories
apk update
apk add tollgate-wrt        # pulls nodogsplash + jq from the packages feed
```

Pre-24.10 (opkg): the `src/gz` line alone is enough — `opkg update` reads
`Packages.gz` from the same directory.

Build-time (SDK/image builder) `feeds.conf` uses the same `src/gz` form:

```
src/gz tollgate https://freedomtechfeed.github.io/feed/<tuple>/
```

## One-time repo setup (owner, manual)

- Enable GitHub Pages: Settings → Pages → Source: `gh-pages` branch.
  The workflow maintains the branch; Pages just serves it.
- (Optional, deferred) index signing key as a repository secret — see the
  TODO block at the end of `build-feed.yml`.
