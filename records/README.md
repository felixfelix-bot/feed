# `records/` — publish records and the tree snapshot

Two different things live here, and the difference matters when you are
recovering a release:

| path | what it is |
|---|---|
| `<channel>-<line>-<arch>.json` | the **publish record** written by `scripts/feed-publish.sh --record`: index sha256, signing key id, every package's sha256/bytes, and the timestamp |
| `tree/` | a **committed snapshot of the generated feed tree** — the public key and the signed index, exactly as published, minus the package payloads. Read `tree/REHEARSAL.md` first: it is test output, not a live channel |
| `tree/manifest.sha256` | the BUILD job's manifest for the payloads the snapshot references |

## Why commit a tree at all

The publish step is deliberately dumb: it downloads, hashes, indexes, signs and
copies — it never compiles (`feed-publish.sh` prints that in the no-rebuild
proof, and fails if any sha256 differs from the build manifest). If the CI box
that ran a publish dies, the release must still be redeployable from a hand-run
of one command. Keeping the generated tree (with its keys and signed index) in
git makes the *mutable* half of the feed durable; the payloads are immutable and
version-named, so they are recoverable by hash from wherever the build job put
them, or by rebuilding the identical package.

**Known gap, stated plainly:** no two-host mirror of the package *payloads*
exists yet. The 7.6 MB `tollgate-wrt-0.6.0_alpha1-r1.apk` referenced by the
snapshot lives only in the build output of the machine that compiled it
(`~/sdk-run/mediatek-filogic/out/`). Mirroring payloads to a second host is the
hosting step's job (`FEED-SERVE-PROVE`), and it is what closes this gap. The
payload's sha256 is recorded here so a mirror can be verified the moment it
exists.

## What the committed snapshot is (and is not)

`tree/` is **a rehearsal**, not the published channel. It was produced by the
reproducible HTTPS gate:

```sh
scripts/get-host-apk-tools.sh --out .feed-tools/apk
export FEED_APK_BIN=$PWD/.feed-tools/apk/bin/apk
tests/feed-https-publish-test.sh \
  --artifacts ~/sdk-run/mediatek-filogic/out \
  --apk-bin "$FEED_APK_BIN" --arch aarch64_cortex-a53
```

That test publishes `tollgate-wrt-0.6.0_alpha1-r1.apk` (7 657 333 B, sha256
`4e0f8654…`) into a tree, serves it over **HTTPS** with the production cache
headers, and asserts the live index lists every package, that each one fetches
200 and matches the build-time sha256, that a corrupted package makes the
assertion fail non-zero, and that the publish touched no artifact. It uses a
**throwaway key pair** created inside the test — the `.pem` here is that
rehearsal key, and its private half was deleted with the test work dir. Never
point a router at `records/tree/`.

The real `prod`/`testing` trees are generated by the publish job (or by hand,
see `docs/feed-index-publishing.md`) into a durable tree directory and mirrored
from there.

## Reading, and restoring, a record

```sh
# what was published, and what it is worth trusting
jq . records/testing-25.12-aarch64_cortex-a53.json

# verify a copy of the payload against the record's hash, wherever it lives
jq -r '.packages[] | "\(.sha256)  \(.filename)"' records/*.json > expected.sha256
sha256sum -c expected.sha256      # from the directory holding the payloads

# rebuild the index+keys from the packages and republish (one command, no build)
scripts/feed-publish.sh --artifacts <dir of .apk> --manifest tree/manifest.sha256 \
  --tree <durable tree> --channel testing --line 25.12 --arch aarch64_cortex-a53 \
  --sign-key <channel key>.sec --keys-dir <public keys dir> \
  --publish-target <host>:/srv/www/feed --base-url https://feed.example
```

## The index is not byte-reproducible — do not compare index hashes

ECDSA signatures are randomised, so two publishes of *identical* inputs produce
different `packages.adb` bytes (measured: 623, 624 and 625 bytes on three runs
of the same inputs).
A record's `index_sha256` identifies **that publish**, not "the" index for a
version. Index correctness is enforced by the signature plus the fetch-back
assertion (every listed filename must 200 and hash to the build manifest), not
by hash equality between publishes.
